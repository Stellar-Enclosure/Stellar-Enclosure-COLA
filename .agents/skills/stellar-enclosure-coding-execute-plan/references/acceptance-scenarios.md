# Acceptance Scenarios

Use these scenarios to review future changes to this skill.

1. **Unrelated staged and unstaged changes coexist while the Step renames and creates files.** The executor verifies the Step candidate independently of unrelated work, stages the exact files including both sides of the rename, reviews the scoped staged diff, commits those paths only, and verifies the original unrelated staged and unstaged contents remain intact.
2. **Step tests pass but no commit exists.** Commit the verified candidate and check its hash and scope before starting a dependent Step.
3. **The Step is already implemented and produces no diff.** Verify recorded Step evidence or prove the complete outcome on a reachable committed baseline with fresh checks. Record verified completion and continue. Dirty-worktree code or an unexplained empty diff cannot establish baseline completion.
4. **A frozen Worker contract needs an internal store file missing from the Plan.** Add the existing store to the Step's file and commit lists, cite the requirement and current caller, validate dependencies and the revised Plan, run the affected tests, and continue under the original authorization.
5. **A validation command fails because a test was renamed.** Verify the new selector covers the same cases, record and strictly validate the Plan correction, then rerun the effective gate. Investigate further if coverage or results differ.
6. **Another person's changes overlap a Step-owned file.** Try a clean worktree and verify that delivery can preserve those edits. If the overlap prevents safe delivery, record the evidence and the exact remedy needed. In both cases keep the other work outside the Step commit.
7. **A later Step exposes an earlier Step defect.** The executor pauses later work, creates a dedicated minimal corrective commit attributed to the earlier Step, reruns affected gates, and does not amend or reset history.
8. **The final audit finds that one internal adapter omits a required validation.** Record an attributed corrective Step, repair it with passing evidence and a scoped commit, then refresh the audit on the new delivery revision. If the only implementation would change an approved contract, report the affected requirement and the necessary decision.
9. **A module test starts a database container.** Verify it creates an isolated, disposable local test database and run the bounded check under execution authorization when no restriction applies. If the only setup is shared or live, seek equivalent authorized evidence. Block the affected Step only if required evidence is still unavailable. Track deferred acceptance separately.
10. **The user says to execute this identifiable Plan, whose header says Review.** Record that instruction as authorization and proceed through structural checks and Step gates. Reuse it on resume. Honor any express pre-execution restriction.
11. **A bundled standards/checklist reference is missing.** Restore the verified resource when available and rerun preflight. Otherwise report the exact missing path and block dependent edits.
12. **The current project is traditional layered.** The Step preserves `biz.controller -> biz.service -> biz.service.impl -> biz.dao`; it does not add generic COLA/DDD packages.
13. **The project uses an exact Egon-COLA Archetype.** The executor rechecks the selected archetype tree/verifier and preserves its modules/dependency direction instead of forcing `biz.*` or a hybrid.
14. **A Step proposes a helper or dependency already covered by Spring/Egon-COLA.** Reuse the existing Starter, component, or abstraction that satisfies the contract. Record the choice and recheck `MC-REUSE-001` and `MC-DEP-001`.
15. **A new carrier is named `UserInfo`, `OrderParam`, or `XxxData`.** `MC-NAME-001` fails until the touched type has its real PO/BO/DTO/VO/Query/Command/Event/boundary role; unrelated legacy names remain untouched.
16. **A reused Command crosses create/update boundaries.** The Step cannot PASS until Jakarta constraints, Validation Groups, group invocation, normalization/error behavior, and focused tests are proven.
17. **A telephone rule is handwritten despite available mature validation.** The executor rejects duplicate parsing/Validator code, uses native Validation/`ValidationUtils`/approved libphonenumber integration, or stops for a proven gap.
18. **A small ordinary DTO is treated as an immutable value object solely because it has few fields.** `MC-MODEL-001` fails. Verify semantics and use the ordinary class Lombok baseline for the DTO. Only a true immutable value object may use a record, subject to the framework and construction checks.
19. **A Service maps objects through setters, BeanUtils, reflection, or JSON.** `MC-CONVERT-001` fails until MapStruct/MapStructPlus and the appropriate Egon converter base own the mapping: `BaseConverter` for bidirectional mapping or `BaseForwardConverter` for irreversible projection.
20. **A Spring Bean has no explicit name, field injection, or an unqualified dependency.** `MC-BEAN-001` fails until stable naming, final dependency fields, `@RequiredArgsConstructor(onConstructor_ = @Autowired)`, and `@Qualifier` propagation to the generated DI constructor are verified.
21. **A configuration key is changed in only one environment.** `MC-CONFIG-001` fails until all profiles are compared and key parity plus typed properties/tests are satisfied.
22. **Complex rules remain a hard-coded switch, and the Spec leaves pattern selection open.** Select a proven pattern that fits the existing variation, record it, implement it, and verify `MC-PATTERN-001`. Keep simple logic direct.
23. **Tests pass but one Manual Check is missing or lacks evidence.** Obtain the evidence and rerun the check. Pending completion gates prohibit a completion commit and dependent Steps.
24. **All Steps passed their local checks, but the final tree violates a standard.** The final audit reruns all 17 IDs and applies the correction procedure. If a finding remains, report it with the evidence-backed verdict and exact missing prerequisite or decision.
25. **Verbatim rules were summarized or corrected.** The literal preservation test fails when either entrypoint or either phase reference changes the exact source, numbering, escapes, spelling, or trailing `&#x20;` text.
26. **Tests pass but Literal Rule evidence is missing.** The Step remains `In Progress`; passing tests cannot replace the ten independent rule rows or permit a commit.
27. **Controller-only Validation.** Controller tests pass, but the Service and DAO/Repository handoffs lack group/invocation checks. Rule 2 and `MC-VALID-001` fail; no commit occurs until every affected crossing is proven.
28. **Reduced complex-object annotations.** The code compiles with only `@Data @Builder`, contrary to the approved complete baseline. Restore the complete Rule 3 implementation and rerun `MC-MODEL-001`. Escalate only if a compliant resolution remains unavailable.
29. **Converter bypass.** A new MapStruct mapper implements neither Egon converter base, or a Service manually copies fields. Rule 3 and `MC-CONVERT-001` fail. Irreversible projections still require `BaseForwardConverter`.
30. **Bean injection almost compliant.** A Bean has Lombok constructor injection but lacks explicit constructor `@Autowired`, or one dependency lacks `@Qualifier`. Rule 4 and `MC-BEAN-001` fail until the emitted constructor annotation and parameter Qualifiers are proven.
31. **One-profile configuration change.** Tests use only dev configuration and pass, but another profile lacks the new key. Rule 7 and `MC-CONFIG-001` fail; the Step cannot commit as complete.
32. **Complex logic uses direct switch.** The Plan requires a State/Strategy pattern but implementation collapses it into a switch. Rule 9 and `MC-PATTERN-001` fail; shorter code is not a waiver.
33. **Final audit repeats only MC IDs.** The final report has 17 Manual Checks but omits the ten literal rules. Final PASS is prohibited until both matrices are independently rerun against final commits.
34. **Execution was interrupted after validating a Step, before committing it.** Verify the recorded revision and baseline, attribute all changes on Step paths, refresh the gates and commit. If a rename or delete is already staged, verify the cached deletion and omit that missing path from the staging command while retaining it for review and commit. If the commit had already succeeded, verify its exact scope and evidence before resuming. Ambiguous ownership or missing evidence that cannot be recovered blocks advancement.
35. **Spec prose uses a stale internal symbol, and the accepted contract and test fix its meaning.** Correct the reference in the smallest Spec passage and update the Plan references and revision metadata. Record the binding evidence and verify the affected requirement. The original authorization covers the clarification.
36. **Two effective Spec passages conflict on which actor may claim a task.** Check governing decisions, published contracts, and tests. If those sources leave a material permission choice open, block the affected Step and report the conflicting rules and exact decision needed.
37. **Strict Plan validation treats a real XML element in an example as an unresolved placeholder.** Confirm the diagnostic from the validator and source, restate the example with equivalent wording while retaining the template's required block structure, rerun strict validation, and record both results. Use an isolated copy when the Plan is frozen. A real missing requirement or gate still needs resolution.
38. **Two internal approaches both preserve observable behavior and satisfy the checks.** Choose the approach that best fits the repository, record the rationale and relevant assumptions, and implement it. The task proceeds without a question about user preference.
39. **The preferred test cannot run, but a repository-standard alternative proves the same behavior.** Confirm equivalent coverage, record the old and new commands and evidence, and continue. Use a comparable before/after test when the Step needs RED and GREEN.
40. **A Step genuinely needs an unavailable dependency or live credential.** Record the exact unmet prerequisite. Park its candidate safely, then finish available independent Steps in a documented dependency-safe order. Report the missing prerequisite and ask only if the user can resolve it.
41. **Before locking a Step, preflight finds a renamed converter and missing validation on a handoff the Step already changes.** Correct the Plan path and symbols, add the needed repair and applicable rule checks to the effective Step, and verify the updated preflight evidence. Lock and implement the Step, then verify the candidate's validation behavior before committing.
42. **Preflight finds that a required earlier Step's adapter regressed.** Verify the cause, make a scoped corrective commit attributed to the earlier Step, and rerun affected checks. Refresh the dependent Step's baseline and continue. If the failure is unrelated and can be isolated without losing required evidence, isolate it and continue the current Step.

- **Builder selection**: A root DTO and an EgonModel PO are added. Expected: choose @Builder for the root construction target and compatible @SuperBuilder across the PO hierarchy when inherited fields must be built; never mix the two.
- **Enum boundary**: A status enum is both persisted and returned to the frontend. Expected: stable @EnumValue and @JsonValue mappings with invalid-input tests.
- **Soft-delete key**: A nullable deleted_at is appended to business uniqueness. Expected: retain the composite key and prove active-row NULL behavior, delete/recreate and old-constraint removal.
- **CQE event**: A local listener logs success. Expected: this is not event delivery; require actual outbox/MQ routing and describe atomicity/recovery limits.
- **Validation extension**: A reusable cross-field rule needs a custom constraint. Expected: @Constraint/ConstraintValidator plus @Valid/@Validated/groups; no utility-only implementation.

- **Unapproved managed dependency**. A tool listed in the BOM is absent from the module. Check existing alternatives first. Request authorization for a specific dependency only when a compliant solution cannot be delivered without it.
- **Selective regeneration conflict**. The user requests mapper XML only after a DDL change, and an existing XML contains manual edits. Preserve custom and unselected files. Try a supported, isolated regeneration path and escalate only if the required output cannot be delivered safely.
- **Unavailable generator**: Only a proposal exists. Expected: report tooling unavailable; do not invent a command or silently generate covered boilerplate by hand.
