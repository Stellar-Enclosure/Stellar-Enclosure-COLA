# stellar-enclosure-source-web

[English](README.md) | [中文](README.zh-CN.md)

`stellar-enclosure-source-web` is generated by `stellar-enclosure-archetype-web` as one independent, organization-only Project. Its Adapter implements the Organization contract published by its own Facade module, and its Infrastructure consumes the Evaluation contract that the peer project publishes.

## Maven Profiles and External Launch Arguments

Use one environment profile at a time: `dev`, `test`, or `prod`; omitted profiles use
`dev` defaults. These profiles configure application startup, while Surefire keeps
its existing `test` profile. JVM heap sizes are examples to tune for the deployment.

From the project root (install sibling modules first for a multi-module project):

```bash
mvn install
mvn -pl stellar-enclosure-source-web-starter -Pdev spring-boot:run
mvn -Pprod -Drun.jvm-args="-Xms1g -Xmx2g" \
  -Drun.server-port=8080 \
  -Drun.config-location=file:/etc/myapp/override.yml package
```

Maven generates `stellar-enclosure-source-web-starter/target/launch.args` during `process-resources`, including when
packaging. Switching profiles or `-Drun.*` values rewrites it even without `clean`.
Only `src/main/launch/launch.args` is filtered by this execution using `@...@`;
existing YAML placeholders remain runtime values. The argument file stays outside the JAR.

Deploy the executable JAR and `launch.args` together, optionally renaming the JAR to
`app.jar`, then launch from the deployment directory:

```bash
java @launch.args -jar app.jar
java @launch.args -Xmx3g -jar app.jar --server.port=9080
```

The file records JVM arguments, the Spring profile, port, and additional configuration
location. These explicit system properties take precedence over corresponding environment
variables; `-Drun.*` overrides Maven defaults, JVM options go before `-jar`, and Spring
command-line overrides go after the JAR. Plain `java -jar` and IDE main-class runs do not
read this file automatically. Relative configuration paths use the launch working directory,
not the argument file directory; use an absolute `file:` path for deployment and forward
slashes for Windows paths. Extra configuration supplements `application.yml` and the
selected `application-{profile}.yml`; omit `optional:` when the file must exist. Keep
credentials in the existing environment/secrets mechanism, never in `run.*` properties.

## Build and Verification

Verify all modules:

```bash
bash ./mvnw -V --no-transfer-progress clean verify
```

`verify` is required rather than `test`: the architecture-governance plugin is bound to
that phase and runs with `unknownLayerPolicy=FAIL`, so a module or class that resolves to
no layer breaks the build.

Package the layered executable jar:

```bash
bash ./mvnw -V --no-transfer-progress -DskipTests package
```

Encrypt a configuration value with a 32-byte key supplied through
`EGON_CONFIG_DECRYPT_KEY` or `EGON_CONFIG_DECRYPT_KEY_FILE`:

```bash
printf '%s' 'plain-text' | EGON_CONFIG_DECRYPT_KEY='replace-with-32-byte-secret-key' \
  bash ./mvnw -q -pl stellar-enclosure-source-web-starter -am -DskipTests compile exec:java \
  -Dexec.mainClass=top.egon.cola.archetype.source.web.starter.config.encryption.ConfigCipherCli
```

`ConfigCipherCli` takes no arguments and reads the plaintext from standard input.
`exec:java` runs it inside the Maven JVM, so the pipe above reaches it. Use the emitted
`ENC(v1:...)` value in configuration.

## CQERS Architecture

Application keeps the existing Manage entry points and delegates each Command, Query, and consumed
business Event to a matching `XxxCmdExe`, `XxxQueryExe`, or `XxxEventExe` under
`application/<domain>/executor/{command,query,event}`. Query execution is read-only. Event executors
handle incoming business events; outbound events go through Domain ports to Infrastructure MQ/Outbox
publishers. Keep the existing transaction, validation, idempotency, and delivery semantics; SSE stream
events are not message-consumption events. The independent Components CRUD generator supports CQERS executors and explicitly configured
inbound events for native Light, Web and Service; Agent and Open profiles are not supported. Review
legacy generated-file ownership and conflicts instead of bypassing them.

## Domain-First Structure

Business-owned code puts the domain before the technical responsibility:

```text
domain/user/entities
application/teaching/manage/impl
application/user/pojo/command
infrastructure/teaching/po
infrastructure/user/repo
adapter/teaching/pojo/dto
adapter/user/facade/impl
```

Shared runtime concerns stay at their layer root. When the optional Evaluation integration is generated, its technical client lives at `infrastructure/client/evaluation` and its Domain service and value objects stay in `domain/teaching`.

## Dependency Graph

```text
common         -> no generated module
domain         -> common
application    -> domain
infrastructure -> domain, optional canonical Evaluation Facade
adapter        -> application, canonical Organization Facade
starter        -> adapter, infrastructure
```

Domain declares the parent-managed Lombok dependency with `provided` scope so code-gen POJOs compile without adding a runtime dependency.

Infrastructure implements Domain-owned ports. Adapter never reaches Infrastructure directly, and Starter contains assembly configuration only. Both canonical Facades are independent artifacts that do not depend on this generated project, so the Web/Service Maven dependency graph cannot cycle.

Persistence uses Common MP repositories and explicit Mapper XML; domain service ports do not inherit technical CRUD types.

## Domains

The complete `user` vertical creates and queries users, assigns roles, grants permissions, caches user reads, and publishes committed changes.

The complete `teaching` vertical creates and queries grades and school classes, caches reads, and publishes committed changes. User-to-class assignment is one Application transaction using both Domain repositories; `school_class_users` is the authoritative membership relationship.

## Runtime Profiles and Integrations

`dev` is the default profile for workstation development and `feature/*` branch verification. It uses the environment-backed PostgreSQL, Redis, RabbitMQ, and COLA RPC integrations.

`test` is selected automatically by Maven tests and is used by the `dev`, `release/*`, and `hotfix/*` validation pipelines. It uses H2 in PostgreSQL compatibility mode, in-memory cache/idempotency adapters, a local event publisher, a deterministic Evaluation query stub, disabled RabbitMQ and external Tianshu connections, and disabled COLA RPC provider/consumer and registry.

`prod` is reserved for runtime builds and deployments from `main`. If the optional peer was supplied, `dev` and `prod` use the COLA RPC Evaluation Facade client with a 3000 ms timeout, zero retries, and startup reference checks. Each consumed Facade has its own group variable — `EVALUATION_COURSE_FACADE_GROUP` (default `course`), `EVALUATION_EXAM_FACADE_GROUP` (default `exam`), and `EVALUATION_SCORE_FACADE_GROUP` (default `score`) — alongside `EVALUATION_FACADE_SERVICE_VERSION` (default `1.0`).


## Integration Ownership

- Adapter owns HTTP `/api/v1/**`, GraphQL `/graphql`, inbound RabbitMQ commands, COLA RPC Facade export, request validation, filters, and protocol conversion.
- Infrastructure owns Common MyBatis-Plus persistence, managed PostgreSQL DDL, Redis adapters, outbound RabbitMQ events, Application-method logging AOP, and the optional Evaluation Facade client adapters.
- Starter owns OpenAPI assembly, runtime profiles, Actuator, Prometheus, Jackson, async execution, and configuration decryption.
- The Organization contract is published by this project itself from its local Facade module. When all four `evaluation-facade.group-id`, `evaluation-facade.artifact-id`, `evaluation-facade.version` and `evaluation-facade.package` values are supplied at generation time, the Evaluation contract is consumed as an external artifact. When they are omitted together, the peer dependency, client, domain service/value objects and configuration are not generated.

When included, the Evaluation query client is an unused integration foundation; no current Application use case calls it.

RabbitMQ command retries use three total attempts with bounded backoff and dead-letter queues. Domain events publish after commit. This example reports exhausted event publication but does not claim transactional-outbox delivery.

## Error Contract

HTTP failures use a stable body containing `code`, `message`, `traceId`, `timestamp`, and `fieldErrors`. Status semantics are `400` validation, `403` forbidden, `404` not found, `409` conflict, `422` Domain rejection, `503` required dependency unavailable, and `500` unexpected failure. GraphQL exposes the same fields through error extensions; Facade failures carry the same code and trace ID.

## Native RPC and Tianshu

This project exposes 10 organization unary operations from the Protobuf contract published by its own Facade module. The optional Evaluation queries use reviewed Service targets, exact methods and matching OAuth bindings.

Production imports an immutable `baseline.json` and uses Tianshu's internal HTTP Service for conditional snapshots and receipts. A dedicated SERVICE registration grants `tianshu:config:read` and `tianshu:config:receipt:write`, together with a separate Pod-bound token projected by the kubelet.

The platform OpenAPI MVC starter preserves business HTTP access. Document governance is disabled by default. Enabling it requires the platform document identity, published groups, complete Shoubing SERVICE verification and `yuheng.openapi.read` scope; published handlers also require explicit `@Operation(operationId = "...")` metadata. Tianquan-Shoubing Servlet filter auto-registration is disabled. HTTP registration follows the effective `server.port`.

The `test` profile uses H2 and local fixtures with native RPC and Tianshu delivery disabled. The managed application supplies the Redis Cluster client for cache and ID leases. Protected configuration is decrypted after Spring Boot Config Data loading.

## Xingyuan Identity and Authorization

The ten REST operations and ten GraphQL roots require an exact-resource verified USER token, the operation's `stellar-enclosure-source-web:<intent>` scope and the separate namespaced RBAC resource/permission. The trusted subject/tenant owns business and MP audit context; actor/role/tenant headers never grant authority. Liveness and readiness probes use the protected management listener. REST and GraphQL writes explicitly check the actual submitted field set against current role field rules before the use case; field-definition caps alone do not permit WRITE.

Ten native RPC methods require verified TENANT SERVICE identity, the fixed application audience and their exact method scope. The shared SDK confirms strict usage proof and restores callback tenant/actor/kind in `finally`; facade metadata keeps correlation/idempotency only and no SYSTEM or synthetic USER fallback. GraphQL uses immutable verified identity/scope/proof/trace plus a framework callback Adapter/Decorator; aliases share one confirmed DENY marker and unavailable state/audit cannot become an ordinary authorization denial.

For the optional Evaluation facade, `EVALUATION_RPC_NAMESPACE` and `EVALUATION_RPC_SERVICE` identify the stable Kubernetes Service. The approved transport and OAuth bindings allow `CourseService/GetCourse`, `ExamService/GetExam`, `ScoreService/GetScore` with matching versions. A standalone generated project has both sets disabled and empty.

Runtime configuration requires explicit trusted HTTPS issuers/JWKs, strict revocation endpoint/epoch, independent control/tenant client credentials and an exclusive audit spool/HMAC key. SDK servlet auto-registration is disabled because the application owns the observation → IdP → RBAC → authorization → trusted business-context chain. Internal RPC uses h2c through the managed Service. The higher-priority document chain accepts fully verified SERVICE tokens with yuheng.openapi.read when governance is enabled; disabled documents are protected. Deployment catalog registration does not grant permissions. External-off tests provide controlled SDK facts; they do not prove live database, Redis, Cilium and browser acceptance.

## Repository, CQE and PostgreSQL

This archetype uses MyBatis-Plus 3.5.16. Business service ports retain domain semantics; concrete repositories extend `EgonColaRepository` and mappers extend `EgonColaMapper`. Queries use explicit XML. `EgonModel` owns id, tenantId, creation/update actors and times, `LocalDateTime deletedAt` and `Long version`: NULL is active, deletion writes a UTC timestamp and increments the version. AR/QueryChain are disabled; technical filling is mandatory.

`APP_DATASOURCE_MODE` defaults to `SHARDING` with LOCAL transactions; enable the `readwrite` Spring profile for the shipped `SHARDING_READWRITE` topology. Single tables use explicit `!SINGLE group.schema.table`; broadcast tables are read-only. Default legacy tenant routing retains its old addresses. The optional `src/test/resources/sharding/two-level-readwrite.yml` example lives in infrastructure for multi-module projects. It hashes tenant_id into a tenant slot, then a business root ID into a bucket; order.id and item.order_id share the same root policy and physical group. This rules-only example is validated by an offline routing test and uses the component's algorithms and `DYNAMIC` transactional reads. It is not loaded as application configuration and does not declare physical data sources or the component write guard; configure those explicitly before deployment.

mix64-v1 is fixed. T/B are powers of two up to 1024, with product at most 4096. Balanced databases also require a balanced slot map and tenant workload. There is no automatic redistribution. Query fanout is bounded; commands require exact keys. Changing topology requires matching DDL and a deliberate data migration/rebuild; the test example is not a drop-in production schema.

The MP-SDJ starter owns datasource/topology setup and contributes the managed `EgonColaPostgreDdlRunner` bean. Called with explicit targets it applies `db/egon-mp/V20260913_001__initialize_repository_schema.sql` to physical PRIMARY schemas from `repository-manifest.json`: empty schemas initialize once, managed schemas verify checksums, prefix and route fingerprint, and non-empty unmanaged schemas fail with REBUILD_REQUIRED. Startup migration is disabled by default. With the `readwrite` profile, `EGON_MP_AUTO_MIGRATE=true` opts in to the three configured physical primary targets and all versions in the manifest; startup validates routed tables and waits for replica WAL replay. The new alignment version renames only empty legacy `_0/_1` shard tables to `_t0/_t1`; it fails on populated shards. Existing managed schemas with a different route fingerprint require a separately planned migration and are not adopted automatically. The archived `db/migration/sharding/**` `B*`/`V*` scripts remain unchanged and are no longer the runtime entry point.

PostgreSQL owns replication. With the `readwrite` profile, ordinary business reads, including reads in a transaction, go to ROUND_ROBIN replicas; writes go to the corresponding primary. Business locking reads and force-primary hints are rejected. Replica lag can make reads stale, including immediately after a write. Cross-group LOCAL writes are rejected and mark rollback-only. No replica provisioning or promotion is implemented.

Activate the environment profile followed by `readwrite` (for example `SPRING_PROFILES_ACTIVE=prod,readwrite`), and provide the three existing primary URLs plus `ORGANIZATION_SHARDING_MASTER_DATA_REPLICA_URL`, `ORGANIZATION_SHARDING_SHARD_0_REPLICA_URL` and `ORGANIZATION_SHARDING_SHARD_1_REPLICA_URL`. Optional `ORGANIZATION_SHARDING_REPLICA_USERNAME` and `ORGANIZATION_SHARDING_REPLICA_PASSWORD` override the shared credentials. Each URL must identify the real replica of its group; switching the mode variable alone does not supply these data sources. Plan and validate any change of topology or historical route fingerprint before migrating existing data.

Managed runtimes acquire their Snowflake lease in Redis Cluster using the approved `EGON_ID_REDIS_ENV` and `EGON_ID_REDIS_APP`. Profiles retain matching MP keys, diagnostics are dev-only and the raw recorder logger is OFF. Dynamic table names require explicit mappings. MybatisBatch runs inside the caller's transaction.

Default tests use isolated H2 and controlled dependencies. This project ships no PostgreSQL-gated test: `-Degon.pg.*` and `EGON_TEST_PG_*` are read by no POM, YAML or test here, and no test starts or provisions a database. Real PG/SS routing, migration and EXPLAIN acceptance remains manual; the absence of a failure is not a pass.

## Two-Level Cache

Cached repository examples use `saveCached`, `updateCachedById` and `removeCachedById` for mutations. When the component cache is active, these methods call its configured consistency strategy with the tenant-scoped key; the ordinary Spring eviction annotation is the fallback when that executor is unavailable. `saveCached` requires an already assigned positive ID. Direct inherited CRUD methods bypass these cache mutation entry points. Configure the cache and MyBatis tenant MDC keys consistently; replica lag can still repopulate an older value until expiry or a later invalidation.

`application.yml`, `application-dev.yml` and `application-prod.yml` ship the cache starter with `egon.cola.component.cache.enabled=true`; `test` keeps the same keys with
`enabled: false` so unit and module runs never require Redis. `infrastructure/config/OrganizationRedisConfig.java` carries
`@EnableCaching`, so a generated project is cache-ready once a Redis connection is configured. The mp-sd-ext
base repository no longer depends on a cache port: concrete repositories declare Spring Cache annotations. The
repository examples use `findCachedById` / `updateCachedById` (Agent defines its own business methods). Ordinary CRUD no
longer evicts implicitly; annotate every relevant write/delete path. Every profile declares the same five TTL keys
(`l1-expire`, `l1-jitter`, `l2-expire`, `l2-jitter`, `null-expire`) plus the shared `key-prefix`, `tenant-mdc-key` and
batch/lock budgets; only the values differ. See
the `stellar-enclosure-component-common-cache-spring-boot-starter` documentation in the Stellar-Enclosure repository
for keys, conditions, combined operations, transactions and sync limitations.

## Java and CQE Coding Requirements

Normal entities use class; record is reserved for immutable value objects. Select @Builder for ordinary construction or compatible @SuperBuilder for inherited fields. Persisted enum codes use @EnumValue; frontend JSON codes use @JsonValue. Reuse Components and Common MP repositories. Validation uses native/custom constraint annotations, @Valid, @Validated and groups; ValidationUtils is a generic manual helper. Soft-delete business uniqueness must combine business columns + deleted_at with active-row NULL enforcement. Event delivery uses the Egon transactional outbox or actual MQ, with explicit transaction/failure and consumer-idempotency semantics. Existing source examples and old SQL must be reviewed against these new requirements; this documentation update does not migrate them.

## UTC Time Contract

All four profiles serialize Java time as ISO strings and declare Jackson UTC. The JVM launch arguments use `-Duser.timezone=UTC`; the existing container templates default to `TZ=UTC` and the same JVM flag. Agent has no container template. Business display zones belong to callers.

Timeline values use `Instant`. Light/Service scheduling and exam Commands follow the shared microsecond contract; this template adds no scheduling or exam feature. An example UTC value is `2026-10-13T01:00:00.123456Z`. `LocalDate` and `LocalTime` represent dates and wall-clock times without zone conversion. Existing `LocalDateTime deletedAt` remains a nullable legacy UTC token: NULL means active, and deletion/version/tenant rules remain unchanged.

The undeployed Light/Service initialization sources use `TIMESTAMP(6) WITH TIME ZONE` for window columns; their existing manifest checksums match the source bytes. This does not migrate deployed data or repair existing SQL history. Existing scheduling uniqueness gaps are outside this change. Real PostgreSQL/JDBC acceptance is separate from offline and H2 tests.

## Permission manifests and controlled delivery

The `permission-producer` profile compiles the API declarations with the Jianshen processor, aggregates a FULL manifest and verifies the final executable. Set the same business/application identity used by the frontend, and provide the real source commit and build ID:

```sh
./mvnw -B -ntp -Ppermission-producer -Dpermission.business=example -Dpermission.application=example-app \
  -Dpermission.commit="$(git rev-parse HEAD)" -Dpermission.buildId=local-review clean verify
```

The checked-in producer inventory and empty targets define no online access. Configure the pinned SDK checkout, contract artifact URL, reviewed target and protected environments before enabling the separate registration/activation workflow. Registration creates a candidate; it neither grants roles nor activates a version. Generated APIs must declare codes within the configured ownership prefix. Existing GraphQL examples retain their own runtime authorization and are not exported as HTTP resources by this profile.

For generated CRUD code, set `apiContract.existingErrorMapper` to `top.egon.cola.archetype.source.web.common.exception.GeneratedCrudErrorMapper`.
