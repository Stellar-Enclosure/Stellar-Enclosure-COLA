# stellar-enclosure-source-light

[English](README.md) | [中文](README.zh-CN.md)

`stellar-enclosure-source-light` is a single Maven module generated by `stellar-enclosure-archetype-light`. It is a deployable monolith whose Java packages enforce the large-monolith light domain architecture; the layers are not Maven child modules.

## Maven Profiles and External Launch Arguments

Use one environment profile at a time: `dev`, `test`, or `prod`; omitted profiles use
`dev` defaults. These profiles configure application startup, while Surefire keeps
its existing `test` profile. JVM heap sizes are examples to tune for the deployment.

From the project root (install sibling modules first for a multi-module project):

```bash
mvn install
mvn -Pdev spring-boot:run
mvn -Pprod -Drun.jvm-args="-Xms1g -Xmx2g" \
  -Drun.server-port=8080 \
  -Drun.config-location=file:/etc/myapp/override.yml package
```

Maven generates `target/launch.args` during `process-resources`, including when
packaging. Switching profiles or `-Drun.*` values rewrites it even without `clean`.
Only `src/main/launch/launch.args` is filtered by this execution using `@...@`;
existing YAML placeholders remain runtime values. The argument file stays outside the JAR.

Deploy the executable JAR and `launch.args` together, optionally renaming the JAR to
`app.jar`, then launch from the deployment directory:

```bash
java @launch.args -jar app.jar
java @launch.args -Xmx3g -jar app.jar --server.port=9080
```

The file records JVM arguments, the Spring profile, port, and additional configuration
location. These explicit system properties take precedence over corresponding environment
variables; `-Drun.*` overrides Maven defaults, JVM options go before `-jar`, and Spring
command-line overrides go after the JAR. Plain `java -jar` and IDE main-class runs do not
read this file automatically. Relative configuration paths use the launch working directory,
not the argument file directory; use an absolute `file:` path for deployment and forward
slashes for Windows paths. Extra configuration supplements `application.yml` and the
selected `application-{profile}.yml`; omit `optional:` when the file must exist. Keep
credentials in the existing environment/secrets mechanism, never in `run.*` properties.

## Build and Verification

Run all tests and architecture checks:

```bash
./mvnw -B -ntp verify
```

`verify` is required. The architecture-governance plugin is bound to that phase, so
`./mvnw test` runs the tests but performs no layer check.

Package the application:

```bash
./mvnw -B -ntp -DskipTests package
```

Run locally after configuring the `dev` integrations:

```bash
./mvnw spring-boot:run
```

## CQERS Architecture

Application keeps the existing Manage entry points and delegates each Command, Query, and consumed
business Event to a matching `XxxCmdExe`, `XxxQueryExe`, or `XxxEventExe` under
`application/<domain>/executor/{command,query,event}`. Query execution is read-only. Event executors
handle incoming business events; outbound events go through Domain ports to Infrastructure MQ/Outbox
publishers. Keep the existing transaction, validation, idempotency, and delivery semantics; SSE stream
events are not message-consumption events. The independent Components CRUD generator supports CQERS executors and explicitly configured
inbound events for native Light, Web and Service; Agent and Open profiles are not supported. Review
legacy generated-file ownership and conflicts instead of bypassing them.

## Domain-First Structure

Business domains come before protocol or technical details so `user` and `teaching` remain cohesive and can later be extracted into independent services without reversing package order.

```text
src/main/java/${packageInPathFormat}
├── start
├── adapter
│   ├── user/{controller,mq,graphql,facade/impl,pojo/{dto,vo,convertor},validators}
│   ├── teaching/{controller,mq,graphql,facade/impl,pojo/{dto,vo,convertor},validators}
│   ├── pojo/{dto,convertor}
│   ├── handler
│   └── filter
├── facade
│   ├── user/{dto,enums,utils}
│   ├── teaching/{dto,enums,utils}
│   └── validation
├── application
│   ├── user/{manage/impl,pojo/{command,query,result,convertor},validators}
│   └── teaching/{manage/impl,pojo/{command,query,result,convertor},validators}
├── domain
│   ├── user/{entities,aggregates,vos,service,validators,enums}
│   └── teaching/{entities,aggregates,vos,service,validators,enums}
├── infrastructure
│   ├── user/{dao,po,converter,repo,service/impl,client/impl,validators}
│   ├── teaching/{dao,po,converter,repo,service/impl,client/impl,validators}
│   ├── aop
│   ├── mq/impl
│   └── config
└── common/{constants,utils,enums,exception}
```

`adapter` owns HTTP, GraphQL, RabbitMQ consumer, and the native RPC providers, which are published directly by the `@EgonRpcProvider`-annotated `facade/impl` classes rather than a wrapper `rpc` package. `facade` owns the stable external contracts, their carriers, contract enums, contract assertions, and the shared validation group; it stays self-contained so it can be published on its own. `application` coordinates use cases and transactions. `domain` owns business state, rules, and the query, event, and idempotency service contracts. `infrastructure` supplies MyBatis-Plus DAOs, `EgonModel` persistence objects, `EgonColaRepository` subclasses, and the implementations of the domain service contracts and outbound clients. `common` holds business-neutral primitives plus the exception roots every layer shares. `start` performs assembly and runtime configuration.

## Dependency Graph

These are the only internal layer dependencies:

```text
start          -> adapter, infrastructure
adapter        -> application, facade
application    -> domain
domain         -> common.exception
infrastructure -> domain, facade
facade         -> common.exception
common         -> no business layer
```

Only the `common.exception` roots may cross into another layer; no other `common` type is imported outside its own layer. Domain Service interfaces live under `domain.<business>.service`; implementations live under `infrastructure.<business>.service.impl`. Application services depend on those contracts and never on an infrastructure type.

`stellar-enclosure-component-bytecode-architecture-maven-plugin` enforces the graph. It is bound to the `verify` phase, maps every `top.egon.cola.archetype.source.light.<layer>` package to its layer, and runs with `unknownLayerPolicy=FAIL`, so a class that lands outside the mapped layers breaks the build instead of being skipped with a warning. Technology-first roots such as `adapter.controller` or `infrastructure.repo` are rejected because they resolve to no layer. The check runs at `verify`; `./mvnw test` alone never reaches it.

## Shared Contracts

Every layer reuses the common-core contracts instead of inventing local ones:

- Exceptions: the `common/exception` roots extend the component `BusinessException` / `CommonException` chain, and the wire code is the stable `getStatus()` string; numeric `getCode()` is never published.
- Enums: handwritten business enums implement `EgonEnum`, so the declared `code` — not `ordinal()` — is the serialized value; `DeletedStatus` and `*FacadeStatus` show the `UNKNOWN` fallback pattern.
- Validation: current BaseValidator/egonColaValidationUtils entrypoints remain source facts. New or changed boundaries must express constraints through native/custom annotations, @Valid, @Validated and groups; the utility is only a generic manual trigger, not the business-rule owner.
- Conversion: DTO/Command/Domain/PO mappings are MapStruct (`@Mapper`) generated and extend `BaseConverter` or `BaseForwardConverter`; a forward-only snapshot projection never gets a reverse method.

## Primary Workflows

1. Create a user after request validation and external identity lookup.
2. Assign an active role to an active user.
3. Grant an active permission to a non-archived role.
4. Create school classes and courses.
5. Schedule a course while enforcing class, course, semester, and time-conflict rules.

HTTP requests carry `X-Tenant-Id` (a Long), `X-Operator-Id`, `X-Request-Id`, and `X-Trace-Id`. The existing filters bind these to `tenantId`, `userId`, `requestId`, and `traceId` in MDC and clear them when the request completes, including failures. Tenant values are normalized before cache and persistence access; malformed or overflowing values return HTTP 400. A missing tenant has no default and tenant-scoped persistence rejects it. Supply or overwrite identity headers at a trusted ingress; these headers are context propagation, not authentication.

REST successes and handled failures use common-core `ResultRecord` (`success`, numeric `code`, string `status`, `message`, `data`, `traceId`, `timestamp`). Existing `ResultRecord` and `PageResultRecord` values are not wrapped again. Business status strings such as `USER_EXISTS` appear in `status`; GraphQL retains its protocol response.

The same Application use cases serve HTTP, GraphQL, COLA RPC, and RabbitMQ entry points. User, permission, school-class, and course queries are implemented through Application boundaries rather than duplicated in protocol adapters.

## Runtime Profiles and Integrations

Persistence uses Common MP repositories and explicit Mapper XML; domain service ports do not inherit technical CRUD types.

`dev` is the default profile for workstation development and `feature/*` branch verification. It uses environment-backed PostgreSQL, Redis, RabbitMQ, COLA RPC, and external HTTP integrations.

`test` is selected automatically by Maven tests and is used by the `dev`, `release/*`, and `hotfix/*` validation pipelines. It uses H2, in-memory adapters, and deterministic stubs; RabbitMQ, Redis, RPC providers and consumers, Tianshu delivery, and external HTTP calls are disabled.

`prod` is reserved for runtime builds and deployments from `main`. Supply PostgreSQL, Redis Cluster, RabbitMQ, Service endpoints and credentials through the platform. RabbitMQ uses Spring connection settings. `RABBITMQ_ENABLED` controls the adapter and listener startup.

## Native RPC and Tianshu

The ten REST operations and four GraphQL root queries require a verified USER Bearer token for this application's exact HTTPS audience. Each entry checks its `stellar-enclosure-source-light:<intent>` OAuth scope and the separate namespaced RBAC resource/permission. `openid` does not grant business access. Identity and tenant come from the verified SDK principal; `X-Tenant-Id` and `X-Operator-Id` have no authority. The protected management listener serves `/actuator/health/liveness` and `/actuator/health/readiness`.

Six REST writes explicitly check the submitted field set before calling the use case: user creation (`externalId`, `name`, `email`), role assignment (`roleCode`), permission grant (`permissionCode`), course creation (`code`, `name`), class creation (`name`, `semester`), and scheduling (`startsAt`, `endsAt`). A field definition's writable cap alone grants nothing: reviewed permission mapping, an effective resource grant and an explicit role field rule must reach the current authorization projection. Missing/READ/NONE policy denies writes. Catalog registration and review/grant are separate operator actions; no endpoint automatically grants access.

All ten unary operations in `src/main/proto/teaching_user_facade.proto` require a verified TENANT SERVICE token, the fixed application resource and that method's exact scope. Providers rebuild write actors from the verified service subject and preserve the original Protobuf success/error contracts. Scope and fine-grained USER permissions are separate authorities. Configure service clients independently with the minimum permitted scopes; never relay USER authority as a SERVICE identity.

The application owns one stateless observation → IdP → RBAC → authorization → business-context chain. The SDK Servlet auto registrations are disabled to avoid duplicate execution. GraphQL captures immutable verified identity, scopes, snapshot, trace and secret-free audit proof; its framework callback Adapter restores these values in a short scope and cleans up in `finally`, including asynchronous completion. A request shares one confirmed DENY marker across aliases. Security errors use the two-field `code`/`message` contract, `no-store`, and `WWW-Authenticate: Bearer` for 401; unavailable state/audit returns 503.

The optional OpenAPI governance chain owns `/v3/api-docs/**` and accepts only a fully verified SERVICE token with `yuheng.openapi.read`. Disabled governance does not make documents public. Business handlers already declare stable operation IDs, `nativeBearer`, and 401/403/503 `NativeSecurityError` schemas; existing business request/response schemas stay unchanged.

Deploy the approved TENANT issuer/JWK bindings, revocation primary and epoch, audit spool, Jianshen endpoint and Redis Cluster. Bind exact tenant IDs to their Spring OAuth2 Client registrations through protected deployment configuration. Kubernetes Service and Cilium GAMMA expose internal h2c. The Downward API supplies the Pod UID and IP, and each application applies the exact business scope.

Tianshu configuration imports an immutable `baseline.json` at startup. The client uses the internal HTTP Service for conditional snapshots and receipts, with a dedicated SERVICE registration scoped to `tianshu:config:read` and `tianshu:config:receipt:write` and a separately projected Pod-bound token. See [Kubernetes delivery](deploy/kubernetes/README.md) for the managed inputs.

## Repository, CQE and PostgreSQL

This archetype uses MyBatis-Plus 3.5.16. Business service ports retain domain semantics; concrete repositories extend `EgonColaRepository` and mappers extend `EgonColaMapper`. Queries use explicit XML. `EgonModel` owns id, tenantId, creation/update actors and times, `LocalDateTime deletedAt` and `Long version`: NULL is active, deletion writes a UTC timestamp and increments the version. AR/QueryChain are disabled; technical filling is mandatory.

`APP_DATASOURCE_MODE` defaults to `SHARDING` with LOCAL transactions; enable the `readwrite` Spring profile for the shipped `SHARDING_READWRITE` topology. Single tables use explicit `!SINGLE group.schema.table`; broadcast tables are read-only. Default legacy tenant routing retains its old addresses. The optional `src/test/resources/sharding/two-level-readwrite.yml` example lives in infrastructure for multi-module projects. It hashes tenant_id into a tenant slot, then a business root ID into a bucket; order.id and item.order_id share the same root policy and physical group. This rules-only example is validated by an offline routing test and uses the component's algorithms and `DYNAMIC` transactional reads. It is not loaded as application configuration and does not declare physical data sources or the component write guard; configure those explicitly before deployment.

mix64-v1 is fixed. T/B are powers of two up to 1024, with product at most 4096. Balanced databases also require a balanced slot map and tenant workload. There is no automatic redistribution. Query fanout is bounded; commands require exact keys. Changing topology requires matching DDL and a deliberate data migration/rebuild; the test example is not a drop-in production schema.

The MP-SDJ starter owns datasource/topology setup and contributes the managed `EgonColaPostgreDdlRunner` bean. Called with explicit targets it applies `db/egon-mp/V20260913_001__initialize_repository_schema.sql` to physical PRIMARY schemas from `repository-manifest.json`: empty schemas initialize once, managed schemas verify checksums, prefix and route fingerprint, and non-empty unmanaged schemas fail with REBUILD_REQUIRED. Startup migration is disabled by default. With the `readwrite` profile, `EGON_MP_AUTO_MIGRATE=true` opts in to the three configured physical primary targets and all versions in the manifest; startup validates routed tables and waits for replica WAL replay. The new alignment version renames only empty legacy `_0/_1` shard tables to `_t0/_t1`; it fails on populated shards. Existing managed schemas with a different route fingerprint require a separately planned migration and are not adopted automatically. The archived `db/migration/sharding/**` `B*`/`V*` scripts remain unchanged and are no longer the runtime entry point.

PostgreSQL owns replication. With the `readwrite` profile, ordinary business reads, including reads in a transaction, go to ROUND_ROBIN replicas; writes go to the corresponding primary. Business locking reads and force-primary hints are rejected. Replica lag can make reads stale, including immediately after a write. Cross-group LOCAL writes are rejected and mark rollback-only. No replica provisioning or promotion is implemented.

Activate the environment profile followed by `readwrite` (for example `SPRING_PROFILES_ACTIVE=prod,readwrite`), and provide the three existing primary URLs plus `LIGHT_SHARDING_MASTER_DATA_REPLICA_URL`, `LIGHT_SHARDING_SHARD_0_REPLICA_URL` and `LIGHT_SHARDING_SHARD_1_REPLICA_URL`. Optional `LIGHT_SHARDING_REPLICA_USERNAME` and `LIGHT_SHARDING_REPLICA_PASSWORD` override the shared credentials. Each URL must identify the real replica of its group; switching the mode variable alone does not supply these data sources. Plan and validate any change of topology or historical route fingerprint before migrating existing data.

Managed runtimes acquire a Common Snowflake lease in Redis Cluster. Set `EGON_ID_REDIS_ENV` and `EGON_ID_REDIS_APP` to the approved issuance pool. Profiles retain matching MP keys, diagnostics are dev-only and the raw recorder logger is OFF. Dynamic table names require explicit mappings. MybatisBatch runs inside the caller's transaction.

Default tests use isolated H2 and controlled dependencies. This project ships no PostgreSQL-gated test: `-Degon.pg.*` and `EGON_TEST_PG_*` are read by no POM, YAML or test here, and no test starts or provisions a database. Real PG/SS routing, migration and EXPLAIN acceptance remains manual; the absence of a failure is not a pass.

## Two-Level Cache

Cached repository examples use `saveCached`, `updateCachedById` and `removeCachedById` for mutations. When the component cache is active, these methods call its configured consistency strategy with the tenant-scoped key; the ordinary Spring eviction annotation is the fallback when that executor is unavailable. `saveCached` requires an already assigned positive ID. Direct inherited CRUD methods bypass these cache mutation entry points. Configure the cache and MyBatis tenant MDC keys consistently; replica lag can still repopulate an older value until expiry or a later invalidation.

`application.yml`, `application-dev.yml` and `application-prod.yml` ship the cache starter with `egon.cola.component.cache.enabled=true`; `test` keeps the same keys with
`enabled: false` so unit and module runs never require Redis. `infrastructure/config/RedisConfig.java` carries `@EnableCaching`,
so a generated project is cache-ready once a Redis connection is configured. The mp-sd-ext base repository no longer depends on
a cache port: concrete repositories declare Spring Cache annotations. The
repository examples use `findCachedById` / `updateCachedById` (Agent defines its own business methods). Ordinary CRUD no
longer evicts implicitly; annotate every relevant write/delete path. See
the `stellar-enclosure-component-common-cache-spring-boot-starter` documentation in the Stellar-Enclosure repository
for keys, conditions, combined operations, transactions and sync limitations. Every profile declares the same five TTL keys
(`l1-expire`, `l1-jitter`, `l2-expire`, `l2-jitter`, `null-expire`) plus the shared `key-prefix`, `tenant-mdc-key` and batch/lock
budgets; only values differ per environment.

## Java and CQE Coding Requirements

Normal entities use class; record is reserved for immutable value objects. Select @Builder for ordinary construction or compatible @SuperBuilder for inherited fields. Persisted enum codes use @EnumValue; frontend JSON codes use @JsonValue. Reuse Components and Common MP repositories. Validation uses native/custom constraint annotations, @Valid, @Validated and groups; ValidationUtils is a generic manual helper. Soft-delete business uniqueness must combine business columns + deleted_at with active-row NULL enforcement. Event delivery uses the Egon transactional outbox or actual MQ, with explicit transaction/failure and consumer-idempotency semantics. Existing source examples and old SQL must be reviewed against these new requirements; this documentation update does not migrate them.

## UTC Time Contract

All four profiles serialize Java time as ISO strings and declare Jackson UTC. The JVM launch arguments use `-Duser.timezone=UTC`; the existing container templates default to `TZ=UTC` and the same JVM flag. Agent has no container template. Business display zones belong to callers.

Timeline values use `Instant`; scheduling and exam Commands truncate both non-null endpoints to microseconds before validation and persistence. Windows require `startsAt < endsAt` after truncation; adjacent half-open windows do not overlap. An example UTC value is `2026-10-13T01:00:00.123456Z`. `LocalDate` and `LocalTime` represent dates and wall-clock times without zone conversion. Existing `LocalDateTime deletedAt` remains a nullable legacy UTC token: NULL means active, and deletion/version/tenant rules remain unchanged.

The undeployed Light/Service initialization sources use `TIMESTAMP(6) WITH TIME ZONE` for window columns; their existing manifest checksums match the source bytes. This does not migrate deployed data or repair existing SQL history. Existing scheduling uniqueness gaps are outside this change. Real PostgreSQL/JDBC acceptance is separate from offline and H2 tests.

The scheduling REST body requires offset-bearing strings, for example `{"startsAt":"2026-10-13T09:00:00.123456789+08:00","endsAt":"2026-10-13T09:30:00.123456789+08:00"}`. Naive or numeric times are rejected; responses use canonical UTC values from the application/domain projection.

Native RPC retains the existing protobuf string time fields and returns UTC `Z` strings; field numbers and carrier types do not change.

## Container Delivery

The generated project uses one source-building `deploy/container/Dockerfile`:

```bash
docker build --build-arg CONTAINER_ENGINE=docker -f deploy/container/Dockerfile -t stellar-enclosure-source-light:local .
podman build --build-arg CONTAINER_ENGINE=podman -f deploy/container/Dockerfile -t stellar-enclosure-source-light:local .
nerdctl build --build-arg CONTAINER_ENGINE=nerdctl -f deploy/container/Dockerfile -t stellar-enclosure-source-light:local .
```

Use the [Kubernetes deployment inputs](deploy/kubernetes/README.md) to deliver a verified image digest. The platform provisions PostgreSQL, Redis Cluster and RabbitMQ separately. Cilium Gateway API and Yuheng manage the public HTTPS entry.

The root `Jenkinsfile` runs tests and can publish immutable images. Set
`PUBLISH_IMAGE=true` plus registry parameters to publish; it never deploys.

Encrypt a configuration value with a 32-byte key supplied through `EGON_CONFIG_DECRYPT_KEY` or `EGON_CONFIG_DECRYPT_KEY_FILE`:

```bash
printf '%s' 'plain-text' | EGON_CONFIG_DECRYPT_KEY='replace-with-32-byte-secret-key' \
  ./mvnw -q -DskipTests compile exec:java \
  -Dexec.mainClass=top.egon.cola.archetype.source.light.start.config.encryption.ConfigCipherCli
```

`ConfigCipherCli` takes no arguments and reads the plaintext from standard input.
`exec:java` runs it inside the Maven JVM, so the pipe above reaches it; a forked
runner such as `spring-boot:run` does not give the CLI a usable stdin.

Use the emitted `ENC(v1:...)` value in configuration. Supply real secrets through environment variables, mounted files, `config/application-secrets.yml`, or `configtree:/run/secrets/`; never commit credentials or decryption keys.


## Permission manifests and controlled delivery

The `permission-producer` profile compiles the API declarations with the Jianshen processor, aggregates a FULL manifest and verifies the final executable. Set the same business/application identity used by the frontend, and provide the real source commit and build ID:

```sh
./mvnw -B -ntp -Ppermission-producer -Dpermission.business=example -Dpermission.application=example-app \
  -Dpermission.commit="$(git rev-parse HEAD)" -Dpermission.buildId=local-review clean verify
```

The checked-in producer inventory and empty targets define no online access. Configure the pinned SDK checkout, contract artifact URL, reviewed target and protected environments before enabling the separate registration/activation workflow. Registration creates a candidate; it neither grants roles nor activates a version. Generated APIs must declare codes within the configured ownership prefix. Existing GraphQL examples retain their own runtime authorization and are not exported as HTTP resources by this profile.

For generated CRUD code, set `apiContract.existingErrorMapper` to `top.egon.cola.archetype.source.light.common.exception.GeneratedCrudErrorMapper`.
